# DECISIONS

Every choice made without asking, with the one-line reason. Where the three reference projects disagreed,
the rule was **follow the most recently committed one**, which is `my-sidepulse`; those rows say so.

## Shape of the project

| Decision | Why |
|---|---|
| SwiftPM, no Xcode project | Two of three reference projects, the most recent included. koffeelid's `.xcodeproj` is generated by XcodeGen and exists for a Metal target ShiftPick has no equivalent of. |
| `swift-tools-version:5.10`, Swift 5 language mode | my-sidepulse and koffeelid; snappy-snap is 6.2 with strict concurrency. **Most recent wins.** It also keeps the event-tap callback free of concurrency ceremony that would have to be got right with nobody to test it tonight. |
| `platforms: [.macOS("26.0")]` | my-sidepulse, written exactly that way; snappy-snap's `.macOS(.v26)` is the same target. |
| XCTest, not swift-testing | my-sidepulse **(most recent)**, and `import Testing` needs tools 6.0, which the row above rules out. |
| `scripts/` (lower case), POSIX `/bin/sh` | my-sidepulse **(most recent)**. snappy-snap uses `Scripts/` and zsh, koffeelid `script/`. |
| Three code targets: `ShiftPickCore`, `ShiftPickPlatform`, `ShiftPickApp`, plus `Tools/axdump` | The family's layering, minus the CLI target: ShiftPick has no command line, because it has no state to ask about and nothing to drive from a key binding. |
| Bundle id `dev.rubens.ShiftPick` | snappy-snap and koffeelid use `dev.rubens.*`; my-sidepulse uses `io.mysidepulse.app` because that app has a domain of its own. ShiftPick has none. |
| The version lives in `VERSION="…"` in `scripts/make-app.sh` | my-sidepulse **(most recent)**; snappy-snap keeps a tracked `Info.plist` instead, and ShiftPick's `Info.plist` is generated. |
| The app's name, bundle id and repository are written **once**, in `scripts/signing.env` | The brief asked for one place. `make-app.sh` writes all three into the built `Info.plist`, including a private `SPUpdateRepository` key, and `Core/AppIdentity.swift` reads them back. Renaming is that file plus four names SwiftPM cannot read from it, listed in `docs/shared/conventions.md`. |

## Behaviour

| Decision | Why |
|---|---|
| The reference point of an item is the **centre of its Accessibility frame** | Measured: Finder reports the icon's own 64 × 64 box and not the cell, so a name that wraps to two lines does not move it. The brief offered the icon centre or its top edge and asked for a measurement; the centre is what the measurement makes stable. |
| The anchor rule is one sentence: **the selected file farthest from the target** | It reproduces both cases the brief names (target after the selection gives the one nearest the start of the range, target before it the one nearest the end) and answers the case it does not name, a target inside the selection, with the widest range the selection justifies. |
| Distance for that rule is flow order where there is one, and screen distance where there is not | A hand-placed folder has no order to count along; the rubber band's natural measure is the plane. |
| A ⌘ Command + ⇧ Shift click with the switch **off** is passed to Finder | "Off" has to mean Finder's own behaviour, as it does for the enable switch. |
| A plain click on empty space inside an icon view **clears the anchor** | Finder has just deselected everything; a later ⇧ Shift click from a file nothing on screen mentions would be a surprise. A click outside Finder leaves the anchor alone. |
| A click is decided **while it is still held**, by a worker the taps' thread waits for, 150 ms and no longer | Measured: one `AXFrame` read costs about 0.06 ms warm, so a full screen of icons costs 6 to 20 ms. The event is answered only once the selection has been set, so nothing is ever swallowed on a guess. The budget is kept by the wait and not by the work: work that checks its own clock keeps no promise when one call does not return. |
| **The click tap is enabled only while ⇧ Shift is held** | An enabled tap that can swallow stalls every click on the Mac the moment its owner loses the Accessibility grant, and no way of noticing that moment is fast or reliable enough to build on. So there is nothing to notice: with no finger on the key the only live tap is a listener, which holds nothing up. Every other defence is a layer under that one. |
| **Only a timeout counts toward the breaker; a disable "for user input" never does** | It is also what a tap is told when its own app disables it, at creation and at every disarm. Counting it opened the breaker at the first install, in one millisecond, and would have again after any three ⇧ Shift releases (`docs/pitfalls.md` 15). A timeout is the stall that costs the user a click. |
| **A click tap that does not take an enable is logged, never acted on** | Whether `tapIsEnabled` answers for an enable made a moment before is not known, and acting on a wrong answer is how a breaker opens by itself. The live question about the grant already covers the one case where it would matter. |
| **A tap macOS disabled is never enabled from its callback**, and three timeouts in a minute end it | macOS disabling a tap that stopped answering is the system's own safety net. Enabling it again from the callback is what turned a second of lost clicks into a hard reboot (`docs/pitfalls.md` 13). Each trip costs one stalled click, so three is the most this app will spend. |
| **Taps are created on the cached answer at launch and on a live one ever after** | A process that has just started reads the grant as it is; one that has been running may be reading the answer from before it was taken away, and the wizard's poll would otherwise ask for a tap every two seconds on the strength of it, under a grant that is gone. A tap that can swallow is born enabled, so the moment it is created should be one in which the grant has just been vouched for. |
| Arming asks the **Dock** a live Accessibility question, and reuses the answer for 2 s | `AXIsProcessTrusted()` is a cached answer that has been seen to be wrong. The Dock is always running, is never the app the user is fighting with, and answers in well under a millisecond; Finder stuck on a network volume would read as a grant nobody can vouch for. Two seconds keeps a burst of capital letters from asking at every one. |
| The lifecycle of the taps is a **value in Core**, and `ClickGuard` only executes it | It is the one part of the app where "every scenario considered" has to be checkable rather than claimed. As a value it is 61 named scenarios and a seeded run of 80,000 events, with no tap, no thread and no permission needed to run them. |
| **Apple events to Finder are not used, and the Automation permission is not asked for** | The brief allows a fallback "if AX exposes only on-screen items", which is true: a 2,500-item folder answers with the 24 to 30 icons that are visible. But the fallback it describes cannot supply what it was expected to. Two measurements on macOS 27, in `docs/pitfalls.md`: `position of every item` answers `{-1, -1}` for every item of an arranged icon view, and `name of every item` answers in **name order** whatever the window's Sort By is. Accessibility is therefore the only source of either geometry or order, and where it stops, ShiftPick lets the click through rather than making a smaller selection the user would not notice was smaller. |
| A collapsed Desktop stack is detected by **having no `AXURL`** | Its `AXRoleDescription` says "Stack", but that sentence is translated; the missing URL is not. |
| The kill switch is a flag the lifecycle reads, not taps that are torn down | It takes effect on the next press of ⇧ Shift either way, and the taps are created once per grant rather than at every flick of a switch. |
| The `com.apple.accessibility.api` notification is **a hint, and what it triggers is: disarm, ask, look again three times** | The brief asks for zero idle cost, and the notification has it. But it is posted for any app's grant, it arrives before the answer changes, and a handler that read the grant once and left is how a revocation went unnoticed here. The 2 s poll runs only while the onboarding wizard is up, which the brief allows. |
| **Away is held against the session at any news, and ⇧ Shift pressed while away is news** | Counting the reasons is what keeps a lid that wakes still locked from arming, and it makes every reason depend on its own notification arriving. `com.apple.screenIsUnlocked` is not even documented. The first ⇧ Shift press after a lost one is somebody at the keyboard, and the moment the feature is wanted; the session is asked then, rather than polled. |
| **No idle poll of the grant**, although every other app with a tap of this kind has one | They need it because their tap is always enabled. Here nothing dangerous exists while idle, a revocation is caught by the live question at the next ⇧ Shift press, and the only timer is the watch kept while the key is down. |
| The onboarding is a four-page wizard, copied from KoffeeLid's along with its skill | The owner asked for the same experience. The skill it came with is the record of a window that had already been got wrong four ways, so copying the window without it would have been copying the look and none of the reasons. |
| Nothing asks for Accessibility at launch any more; only the wizard's own button does | The `macos-building-onboarding` skill's hardest rule, and the owner overruled the old §7 for it: a prompt nobody clicked for arrives with no explanation beside it, and macOS remembers a refusal for good. |
| The wizard stays open when the grant arrives, instead of closing itself | The run on which the permission is granted was the one run where the pitch and *All set* were never read. The row ticking over to *Granted* says the same thing and lets the user finish. |
| The wizard's row is titled *Device Control and Data Access*, not *Accessibility* | That is what the Privacy & Security pane's own strings call it on macOS 27, and the user has to find it in that list. The word they came looking for is in the line under it. `docs/pitfalls.md` 10. |
| One poll, owned by the wizard, replacing the app's own permission timer | Two timers watched the same grant, and the app's was started when the window opened and stopped only when the grant arrived, so a window closed first left it running for the life of the process. |
| `Open at Login` and `Show in menu bar` are the optional page, and notifications are not | Notification permission is still asked the first time there is something to announce and for nothing else (§8), so a row that asked for it early would have overruled that for no gain. |
| A second copy asks the running one for its window **with a distributed notification** | Opening the running copy's bundle from a process about to exit was measured to reach nobody. An Apple event would need the Automation grant this app never asks for. A notification needs nothing, and the worst anybody else can do by posting it is bring a window forward. |

## The Settings window

| Decision | Why |
|---|---|
| Four pages: General, Selection, System, Tip | The skill's rule: General first, then the features in the order a user meets them, then System, then Tip last. ShiftPick has one feature, so it has one feature page. |
| "About" is the app icon at the top of General and the version row in Updates | That is what the three reference projects do; none of them has an About window or an About group. |
| The **Open Accessibility Settings** button and its warning show only while the permission is missing | `macos-building-settings-pages` states it: "once green, button and warning go and **the row stays**". snappy-snap's own System page keeps the button always; the skill is the authority and it is the newer statement of the rule. |
| A second group, **Clicks**, reports whether the tap is up | It is the one failure that is otherwise completely silent: the permission granted, the app on, and macOS refusing the tap anyway. Silence is a defect. |
| No control was invented for anything | Two switches, two status rows, buttons. Nothing needed a control the skill has not chosen. |

## Tooling and packaging

| Decision | Why |
|---|---|
| `scripts/install.sh` quits the running copy with `pkill`, not with an Apple event | snappy-snap sends `tell application id … to quit`, which needs an Automation grant the script cannot be sure of, shows a dialog when it is missing, and **launches the app** when it is not running. ShiftPick has no state to flush on the way out. |
| The install helper has no launchd branch | my-sidepulse's helper can start the app through its launch agent. ShiftPick has no launch agent, so the branch would be a stub, and a stub is what the brief forbids. |
| The app icon is a placeholder generated by `scripts/make-icon-preview.swift` | The brief allows a placeholder icon. It is the same three-bar mark the menu-bar item draws, so the two agree; `Resources/ICON-NOTES.md` says what replacing it means. |
| A `LICENSE` file, MIT | The brief asked for one. **None of the three reference projects carries a licence**, and my-sidepulse's README says "Personal build: no licensing", so there was no house style to follow; MIT is the least surprising choice for a free personal tool with a Ko-fi link, and the owner can replace or delete it. |
| A `CHANGELOG.md` | The brief asked for one. No reference project has one either; its style is the commit titles', which is the only changelog those projects keep. |
| `docs/manual-test-checklist.md` at the root | The brief named that file and that place. The reference projects call it `docs/manual-test-checklist.md`; `docs/README.md` points at the root file so the index still works. |

## Open and Save panels (the stretch goal)

| Decision | Why |
|---|---|
| **Taken, and kept** | It was held to the brief's two conditions and passes both: it needs no change on the Finder path, and it works. Three things were measured before a line was written: a panel's icon view has Finder's hierarchy identifier for identifier; `AXSelectedChildren` on it is settable and takes a range of any size; and **its own ⇧ Shift click has exactly the same gap**, selecting the first and third icon of a row and leaving the second alone. Without that third measurement the feature would have been redundant. |
| A panel is recognised by its window's `AXIdentifier` | `open-panel` and `save-panel` are AppKit's own and are not translated, unlike the role descriptions beside them. They are the "role-based alternative" the brief asks for, and they are the *only* two things that get past the process check: another application's collection view, however much it looks like one, is somebody else's control. |
| The rename check is **not** made for a panel | A Save panel keeps its name field focused the whole time it is up, so asking Finder's question of a panel would refuse every click in it. |
| The application brought forward is the panel's own, not Finder | That is what the click would have done. |
| The window is found by walking the chain, not by asking for `AXWindow` | Measured: a panel's collection list answers `kAXErrorNoValue` for `AXWindow`, where Finder's answers with its window. |

## What was left out, and why

- **The uninstall does not reset the notification authorization.** No public API does, and the way around is
  to rewrite `usernoted`'s private preferences, which hold every app's answer, and to kill two system
  daemons. An uninstall touches only what is ShiftPick's own; a reinstall inherits the old answer.

- **No tap in a helper process.** A second process that owns the taps can be killed by the first, which is
  the one remedy that always works; but it needs a nested signature, a second identity for the privacy
  database to reason about, and a channel between the two, and what it buys over a tap that is only enabled
  while ⇧ Shift is held is a case that already heals itself after one stalled click.
- **No listen-only tap with the selection put right afterwards.** It cannot hold anything up by construction.
  It also lets Finder toggle the clicked file first, so every ⇧ Shift click flickers, and the fix-up races
  Finder's own handling of the release: a wrong selection nobody noticed, followed by ⌘ Command ⌫ Delete, is
  its own way of breaking somebody's computer.

- **No Apple events, no Automation permission.** See above: measured, not assumed.
- **No `ShiftPickCLI`.** The reference apps' command lines exist to drive state from a key binding; ShiftPick
  has one switch, and it is in the menu.
- **No launch agent.** The reference apps that have one need to survive a crash unnoticed. ShiftPick's
  failure is visible the moment a ⇧ Shift click does the old thing, and `SMAppService.mainApp` is what the
  closest sibling uses.
